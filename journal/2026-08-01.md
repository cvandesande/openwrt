## Git signing was silently broken

`~/.gitconfig` had been reduced to `user.name` and `user.email` — 53 bytes,
mtime the same morning. Every signing setting was gone, so commits were being
made unsigned, which AGENTS.md treats as a blocker rather than a fallback. The
tell was `%G?` reporting `N` on `openwrt` HEAD `e0f3432358 "update build
tools"`, and ask-cdx logs erroring with `gpg.ssh.allowedSignersFile needs to be
configured`.

`nixos-config` does not supply this and is not meant to: `programs.git.config`
in `modules/profiles/dev-toolchain.nix` sets identity only, deliberately, so
`flake-lock-commit.service` can commit on a fresh install before any
`~/.gitconfig` exists.

Restored globally: `gpg.format=ssh`, `user.signingkey` →
`~/.ssh/id_ed25519_sk.pub`, `commit.gpgsign`/`tag.gpgsign` true, and a new
`~/.ssh/allowed_signers` (mode 600) wired to `gpg.ssh.allowedSignersFile`. The
two prior ask-cdx commits then verified `G`. `5eb7990 "Harden CDX control and
IPsec paths"` is genuinely unsigned and stays that way.

The key is a YubiKey FIDO2 credential (`sk-ssh-ed25519`, application
`ssh:opendmz`), so **every commit and every push costs a physical touch** — a
rebase of N commits is N touches. `ssh-add -L` reports no identities and that
is fine: `ssh-keygen -Y sign` reads the key file directly. Do not "fix" the
empty agent by enabling `gnupg.agent.enableSSHSupport`; the comment in
`modules/profiles/applications.nix` records that gpg-agent previously shadowed
the FIDO2 key with an OpenPGP auth subkey that has touch confirmation
**disabled**.

## #29: the port cap is real, and OFFLINE ports count against it

Traced the whole chain in source rather than trusting the issue's summary.

`dpa_app` sets `finfo->max_ports` from the raw fmc `port_count`
(`dpa.c:815`) and has no cap of its own, so every `<port>` in `cdx_cfg.xml`
counts — OFFLINE included. The kernel rejects anything above
`CDX_CTRL_MAX_PORTS_PER_FMAN` twice, in `get_port_info()` (`dpa_cfg.c:348`)
and in the ioctl validation loop (`dpa_cfg.c:797`). OH ports are then walked
out of that same bounded `finfo->portinfo` array (`dpa_cfg.c:841`) through
`cdx_add_oh_iface` → `dpa_add_oh_if` → `cdxdrv_create_of_fqs`, which is the
**only** site that sets `PORT_VALID` (`devoh.c:795`) — the flag
`alloc_offline_port()` scans for. No cfg entry, no valid port, hence
`ipsec_init_ohport ... failed`. That message is a consequence, not a fault.

Confirmed soft, not structural: the port table is `kcalloc`'d from
`max_ports`, OH ports carry a separate `MAX_OF_PORTS=4`, and no fixed `[5]`
array exists on the port path. `git log` on `cdx_ioctl.h` shows the value
arrived in the 2026-04-25 vendor import — this fork never lowered it.

### The off-by-one that would have bound the wrong port

`number="1"` is the **IPsec** port. `dpa.c:361` formats the device name as
`"dpa-fman0-oh@%d"` with `index + 1` → `dpa-fman0-oh@2`, which
`ohport_assign[]` (`devoh.c:64`) binds to `PORT_TYPE_IPSEC`. `number="2"` →
`oh@3` → WiFi. Corroborated three ways: the sprintf, the DTS node name, and
the vendor `cdx_cfg_*.xml` convention pairing `cdx_port_of2_policy` with
`oh@2`. Worth checking every time — the failure would be silent and would look
like IPsec offload simply not working.

### Two of the issue's residual risks look smaller than written

Both re-read from source; neither is a hardware measurement.

- **FIFO budget is not the blocker #29 suggests.** `total-fifo-size = 0x3e500`
  (255,232 B) against 250,624 B declared across 6×1G (153,600) + 2×10G
  (81,920) + both OH ports (15,104) — and three 1G MACs are `status =
  "disabled"`. No DTS change needed.
- **KeyGen schemes do not scale per port.** All ten policies in the vendor
  `cdx_pcd.xml` reference the same twelve distributions, and five ports
  already work, so fmc is sharing them. A sixth port adds a port-PCD binding,
  not new schemes.

Still open, and only bench time closes them: whether the FMan microcode blob
carries its own port-count assumption, and whether the SDK FMan driver's
runtime FIFO accounting matches the DTS declaration. Both fail as a dead
dataplane at boot.

## Risk investigation — the cap was ours, and it hid two bugs

Follow-up session on #29's residual risks. Source-only; nothing built or run.

### Correction: "the cap came from the vendor import" was wrong

Stated earlier in the session on the strength of `gh api` showing
`cdx_ioctl.h`'s history starting at the 2026-04-25 import. That is one source
treated as a conclusion — the *file* existed at import, the *constant* did
not. The pristine vendor `cdx-5.03.1`, bundled inside the ASK tarball that
`ask-dpa-app` pins, has **no `CDX_CTRL_MAX_*` constants at all**.

`git log -S` settles it: `32f4a48 "Harden CDX dataplane control paths"` (this
project, 2026-04-27) introduced them, replacing an unbounded
`kzalloc(mem_size, 0)` fed by a userspace `max_ports`. The bound is our own
anti-overflow guard. The value 5 was copied from vendor `MAX_PORTS_PER_FMAN`
in `cdx_common.h`, whose only upstream reference is a **commented-out**
declaration — dead even in vendor code. Every vendor sample config exceeds it
(`cdx_cfg.xml` 9 ports, `_dgw` 8, `_ls1046_rdb` 8, `_rgw` 7), so it never
matched their own configurations.

Raised to **16**, derived rather than chosen: `finfo->max_ports` is fmc's
`cmodel.fman[].port_count`, which indexes `ports[FMC_PORTS_PER_FMAN]` with
`FMC_PORTS_PER_FMAN == 16`. A larger value cannot come from a working
`dpa_app`. Correct for every SoC the header covers, and WiFi needs no further
kernel change.

### Risks retired

- **FIFO, BMI tasks, open DMAs — not affected at all.** All three are
  accumulated budgets committed at **FMan port init**, and both
  `fm_port_match[]` (`fsl,fman-port-oh`) and `offline_port.c` (`fsl,dpa-oh`)
  bind straight from the DTS. Both OH ports already probe and already hold
  their allocation on the running box. `cdx_cfg.xml` only decides whether CDX
  *uses* an already-initialised port. The earlier static FIFO arithmetic in
  this entry reached the right answer for the wrong reason, and had omitted
  `extraFifoPoolSize` besides (harmless here — every DTS port declares extra
  fifo `0x00`).
- **Microcode carries no port-count assumption.** The blob is keyed to SoC and
  FMan revision (`fsl_fman_ucode_ls1046_r1.0_106_4_18.bin`); nothing reads
  port-count capability from it.
- **KeyGen schemes are shared.** Hardware allows 32; `cdx_pcd.xml` defines 16
  distributions, all `shared="true"`. Proof they are shared rather than
  per-port: 5 ports x 12 distributions = 60 > 32, and 5 ports work today.
- **Bitmask width is fine** (`port_idx` is `uint32_t`), but there is a hard
  portid ceiling worth knowing: `<combine portid="true" offset="16"
  mask="0xF"/>` in every distribution means **portid must be <= 15**.

### Two bugs on the path the change unblocks

Both fixed in ask-cdx `40298bd`, pinned as r53.

1. **`get_tableInfo_by_portid()` compared a bitmap with `==`.** `port_idx` is a
   bitmap built by `dpa_app` as `tbl_info->port_idx |= (1 << port->portid)`
   (`create_tbl_portmap()`). With all classifications `shared="true"`, any
   table reachable from more than one port has several bits set, so
   `== (1 << portid)` can never match. The sibling `dpa_get_tdinfo()` already
   used `&`. Never fired because the only caller, `get_ofport_info()`, is
   reached solely from `ipsec_init_ohport()` and the WiFi equivalent, and both
   OFFLINE ports were absent from the config so `alloc_offline_port()` failed
   first. **Re-adding portid 9 is what executes it for the first time.**
   Unfixed, the failure is silent: `get_ofport_info()` still returns 0 and
   `dpa_ipsec_ofport_td()` hands NULL table descriptors to outbound SA
   insertion (`cdx_dpa_ipsec.c:2601`) and inbound SA setup (`:196`).
2. **`dpa_add_oh_if()` never bounded the indices it parsed** out of the
   config-derived port name before `cdxdrv_create_of_fqs()` used them to index
   `offline_port_info[MAX_FRAME_MANAGERS][MAX_OF_PORTS]`. The OH array index is
   the configured `number` verbatim, so `number >= MAX_OF_PORTS` is an
   out-of-bounds kernel write; `port_idx == 0` would wrap the unsigned
   subtraction and overrun `oh_iface_name[8]`. Latent — the DTS declares only
   `oh@2`/`oh@3` — but this is the check that actually enforces
   `MAX_OF_PORTS`.

Also noted, not fixed: `get_tableInfo_by_portid()` ORs `1 << tinfo->type` into
`info->flags`, where table types 8/9 alias `OF_FQID_VALID`/`IN_USE`. Harmless
on first init (struct zeroed, both flags already set) but
`release_offline_port()` never clears `td[]`, so a release/re-alloc cycle
would hand out stale descriptors. Matters for module reload and `cmm restart`,
not a cold boot.

### Open

Medium confidence on bug 1's failure shape: if fmc leaves an OFFLINE port's
`ccnodes[]` empty then `&` will not match either and the fix is larger. One
bench boot distinguishes them.

A zero-risk pre-check is available with no build or flash: the OH ports
already probe on the production router, so their FMan init and FIFO/task/DMA
commitment are visible in the current boot log.

### Build environment: the host loader fix moved

The cold build failed at `policycoreutils/host` with `msgfmt: error while
loading shared libraries: libselinux.so.1`. Root cause is nixpkgs' ld-wrapper
injecting a dead relative `outputs/out/lib` RUNPATH into host links — 52 of 77

FHS profile, guarded on `rules.mk` — no rebase surface, and it covers all 52
binaries rather than one package. openwrt `aaead1150c`.

## r55

Two changes, in `ask-cdx` `0f99015`.

`CDX_CTRL_MAX_TABLES_PER_FMAN` 64 → 1024, derived the same way r53 derived the
port ceiling. `num_tables` bounds a `kcalloc()` of a userspace-supplied count
and sizes no array — checked with grep for `[CDX_CTRL_MAX_TABLES_PER_FMAN]` and
for any static table array, none exist. dpa_app's `get_table_info()` sets it to
`cmodel.ccnode_count + cmodel.htnode_count`, and both index arrays declared
`[FMC_CC_NODES_NUM]` with `FMC_CC_NODES_NUM == 512` (`fmc.h`), so 1024 is the
tightest bound a working dpa_app cannot exceed. Sixteen ports at the observed
ratio is 192.

Second, a bug found while verifying the first. `get_tableInfo_by_portid()` did

```c
td[tinfo->type] = tinfo->id;
```

where `td` is `void *[MAX_MATCH_TABLES]` (12, with `CDX_RTP_RELAY` undefined)
and `tinfo->type` arrives via `get_cctbl_info()`'s `copy_from_user()` with no
validation anywhere in between. An unknown table type in the PCD writes past
the caller's array. `dpa_ipsec.c:3824` bounds the identical index; this path
did not. Now it does, and logs when it fires.

That second change is in scope rather than drive-by: the OFFLINE port is new,
and if it carries a table type the kernel enum does not cover, the old code
corrupts kernel memory silently while the new code names it.

Also noticed, not fixed: `get_table_info()` sets `fman_info->num_tables` to the
model-wide node count *before* filtering by fman index, and the per-fman count
it computes afterwards only feeds a debug print. Harmless on a single-FMan
part; wrong on a two-FMan one. Not touched — no hardware to test it on.

### The failsafe

Rather than take the downtime, armed a one-shot script from `/etc/rc.local`:
if the six-port boot failed it would dump `dmesg` and the dpa_app log to
`/root`, restore the 5-port backup, and reboot. Two layers — dmesg checks at
30s for failures the kernel reports, then a 900s deadman for failures it
cannot see, like a dead LAN. Self-disarming, because after a revert the
OFFLINE line is gone and the script exits immediately; and it refuses to act
at all if the backup is missing or itself six-port, so it cannot loop.

It logged `armed on six-port config` then `boot looks good, waiting 900s`, and
was disarmed by `touch /root/.cdx-6port-confirmed`.

Worth keeping as a pattern: the bench trip was never about the *editing*, it
was about needing a human present to recover. A boot that can diagnose and
revert itself removes the reason for the trip. The residue is untracked state
on production — `/root/cdx-6port-failsafe.sh` and the `rc.local` hook — which
should come off once #29 closes.

```
[  519.825670] IPSEC_COMPAT_FQ: create fqid=0x81ef channel=0x801 wq=3 sa=0x0
```

`cmm -c "query sa"` showed both SAs in the hardware table with SPIs matching
swanctl exactly — `c94964bb` in, `c0945d09` out, ESP-Tunnel, AES-GCM-ICV16.

### The proof

Streaming video from a camera at 192.168.8.32 on the remote subnet, to a
workstation at 192.168.12.8 on the local one, so the router is *forwarding*
rather than originating:

| | inbound `c94964bb` | outbound `c0945d09` |
|---|---|---|
| SEC engine, sample 1 | 5891 pkts / 5,711,548 B | 2737 pkts / 222,808 B |
| SEC engine, sample 2 | 8116 pkts / 7,136,218 B | 3983 pkts / 290,640 B |
| Kernel, both samples | 0 / 0 | 0 / 0 |

Hardware counters advance in real time; the kernel IPsec stack stays at exactly
zero. `CPU: 0% usr 0% sys 100% idle 0% sirq` during the stream — zero softirq
is the part that matters, since that is where kernel packet processing would
land. ICV failures, HW errors, and protocol format errors all zero. The flow is
`fp-state: installed`, `local-conn: no`, `fpp-dir: orig+reply(0x3)`,
`orig-oif: pppoe-wan10g`.

The byte ratio is a sanity check in its own right: 7.1 MB in against 291 KB
out is a video stream and its ACKs, not a synthetic test.

Traffic cannot be travelling unencrypted — the remote is RFC1918 and answers —
and the kernel is demonstrably not encrypting it. Therefore the SEC engine is,
which is what the counters say directly.

### A new silent-lie trap

Earlier in this session I reported "zero SAs, zero policies" from
`ip xfrm state | grep -c ^src`. That was worthless evidence: `/sbin/ip` is
`ip-tiny`, which has no `xfrm` object at all. It prints `Object "xfrm" is
unknown` to *stderr* and **exits 0**, so the pipeline counts zero lines and
looks like a clean negative result.

The conclusion was accidentally correct — the tunnel really was down at that
moment, which `swanctl --list-sas` and the charon log did show — but the check
cited for it could not have detected the opposite. Exactly the failure shape
`AGENTS.md` already warns about with `ausearch` and `ubus network.device
status`: fails in the direction that looks like success. Added to that list.

The lesson that generalises: when a tool reports absence, confirm the tool can
represent presence. `ip help` lists the objects a given build supports.

## #33 — yul_tunnel does not establish after reboot

Fixed and verified hands-off on hardware. The tunnel now comes up after a cold
boot with no manual `swanctl --initiate`.

The board is on the `mono-ask` bench build for #29 — kernel 6.18.39,
`kmod-ask-cdx` r55, `ask-dpa-app` r5, `OpenWrt SNAPSHOT r35761+1-83c1d75858` —
not the 25.12.5-mono1 production image. Scope every claim below to that build.

### The issue named one failure mode; there were two

The reported one is real and is a specific code path, not a timing accident.
`libcharon/sa/ike_sa.c:1596`:

```c
if (!this->retry_initiate_interval)
{
    DBG1(DBG_IKE, "unable to resolve %s, initiate aborted", ...);
    return DESTROY_ME;
}
DBG1(DBG_IKE, "unable to resolve %s, retrying in %ds", ...);
defer_initiate = TRUE;
```

The logged `initiate aborted` *is* the `retry_initiate_interval == 0` branch.
Stock `/etc/strongswan.d/charon.conf:266` documents the knob with this exact
failure as its example: "Interval in seconds to use when retrying to initiate
an IKE_SA (e.g. if DNS resolution failed), 0 to disable retries."

So I set it, kept `startaction start`, and rebooted. The retry worked:

```
16:18:54  vici initiating 'yul_tunnel'
16:18:59  resolving 'yul.opendmz.com' failed: Try again
16:18:59  unable to resolve yul.opendmz.com, retrying in 5s     <- was "initiate aborted"
16:19:00  interface pppoe-wan10g activated
16:19:04  initiating IKE_SA yul[1] to 174.94.108.224
16:19:04  received NO_PROPOSAL_CHOSEN notify error
```

And the tunnel still did not come up. **The WAN IP changes on every reboot**
(84.203.4.207 -> 84.203.5.210 -> 84.203.6.5 across three boots) and DDNS takes
minutes to propagate, so the peer rejects the initiate until its resolution of
`ork.opendmz.com` catches up. `retry_initiate_interval` does not cover that: it
only defers on *resolution* failure. Nor does `keyingtries`, which governs
retransmission of unanswered packets — an explicit error notify destroys the
IKE_SA, and `start_action = start` is one-shot, so nothing ever retried.

### `startaction route` was the right call all along

The issue recommended it; I argued for the retry knob instead and was wrong.
The property that matters here is not "retry once DNS resolves" but "keep
retrying indefinitely until the far end agrees", and only the trap policy has
it — it re-arms on every matching packet.

| Failure at boot | `retry_initiate_interval` | `startaction route` |
|---|---|---|
| DNS not resolvable yet | closes it | closes it |
| DDNS stale -> `NO_PROPOSAL_CHOSEN` | **no** — one-shot, gone | closes it |

I had also flagged trap as risky because acquire-driven SA creation was
untested against the CDX offload path. That concern was unfounded, and is now
disproven rather than merely unexercised — see the counters below.

### Hands-off reboot, the acceptance run

Boot at 16:25:40. Nothing touched afterwards; the acquires come from real LAN
traffic, the workstation at 192.168.12.8 reaching the camera at 192.168.8.32 —
the same flow as the #29 proof.

```
16:26:01  creating acquire job for policy 192.168.12.8/32[icmp/8] === 192.168.8.32/32[icmp/8] ... seq {1}
16:26:01  initiating IKE_SA yul[1] -> NO_PROPOSAL_CHOSEN
16:28:47  acquire ... seq {2} -> initiating IKE_SA yul[2] -> NO_PROPOSAL_CHOSEN
16:31:33  acquire ... seq {3} -> initiating IKE_SA yul[3]
16:31:33  IKE_SA yul[3] established between 84.203.6.5[ork.opendmz.com]...174.94.108.224[yul.opendmz.com]
16:31:33  CHILD_SA yul_tunnel{2} established with SPIs caecaeb2_i c915d492_o
```

Three attempts over six minutes, self-healing as DDNS propagated. `swanctl
--list-sas` shows the CHILD_SA `INSTALLED`; `cmm -c "show stat ipsec query"`
shows two entries with SPIs `caecaeb2` and `c915d492`, matching swanctl
exactly. Acceptance criterion met in full.

Offload holds on the acquire-created SA, checked the way #29 was — hardware
advancing while the kernel stays pinned at zero:

| | inbound | outbound |
|---|---|---|
| SEC engine, sample 1 | 55 pkts | 56 pkts |
| SEC engine, sample 2 (+20s) | 75 pkts | 76 pkts |
| Kernel, both samples | 0 / 0 | 0 / 0 |

### What is deployed

All three are runtime config on the router. No code change, no build, no
package rebuild, nothing to port between branches.

| Change | Where | Verdict |
|---|---|---|
| `retry_initiate_interval = 5s` | `/etc/strongswan.d/charon-retry-initiate.conf` (new) | works, but insufficient alone |
| `startaction 'route'` -> `start_action = trap` | `uci ipsec.yul_tunnel.startaction` | **this is the fix** |
| `closeaction 'hold'` -> `close_action = trap` | `uci ipsec.yul_tunnel.closeaction` | coherence with trap semantics |
| `keyingtries '%forever'` -> `keyingtries = 0` | `uci ipsec.yul.keyingtries` | did not help; harmless, kept |

Both survive sysupgrade: `/lib/upgrade/keep.d/strongswan` keeps
`/etc/strongswan.d/`, and `/etc/config/` is kept as standard. That means the
fix carries onto `mono-ask-25.12` when it is next flashed — but carrying is not
verifying, and **it has not been verified on 25.12**.

I kept `retry_initiate_interval` even though trap alone would likely do. With
trap, charon initiates on acquire rather than at load, so the resolution race
mostly disappears; the retry still covers an acquire that fires while DNS is
briefly unavailable. Cheap, and it fails safe.

### Two things checked and left alone

`swanctl.init:305` warns "Closeaction ... can cause instability" on every
reload. It fires for *any* non-`none` closeaction, not for the value — the
warning is unconditional, so switching `restart` -> `hold` did not silence it
and was never going to.

The issue's side note about `failed to create XFRM interface 'xfrmi-test-2007'`
is confirmed benign: `target/linux/generic/config-6.12:7762` has
`# CONFIG_XFRM_INTERFACE is not set`, with no layerscape override. charon is
probing for a compiled-out feature. Route-based IPsec would need it; this
policy-based tunnel does not.

### Not fixed

The WAN-IP-changes-on-reboot / DDNS-lag interaction is now *tolerated*, not
solved — the tunnel is simply down for the few minutes propagation takes. If
that window ever matters, the fix is on the peer side (shorter TTL, or matching
by ID rather than resolved address), not here.

## #29 ported to `mono-ask-25.12`, built, flashed, proven

Everything above happened on `mono-ask` at kernel 6.18.39. `mono-ask-25.12` at
6.12.94 is what actually gets flashed, so none of it was real until it ran
there. It does now.

### The port

Collapsed the four `mono-ask` commits (`e879859`, `52af9fc`, `33af438`,
`0bd3fd8`) to their end state as `9ec05f6134`. The intermediate r52/r53/r54
pins were diagnostic steps and are not reproduced on the release line — there
is no reason for 25.12 to carry a pin whose only purpose was to make a silent
rejection loud.

Three files, byte-identical to `mono-ask` afterwards:

| File | Change |
|---|---|
| `package/kernel/ask-cdx/Makefile` | pin `b1317a1` -> `0f99015`, release 51 -> 55, mirror hash |
| `package/network/ask-dpa-app/Makefile` | release 4 -> 5 |
| `.../ask-dpa-app/files/cdx_cfg.xml` | re-add `portid="9"`, `type="OFFLINE"` |

Checked before applying, because a clean cherry-pick proves nothing about
whether the target branch can carry the change: `0f99015` is a descendant of
the `b1317a1` this branch already pinned, so no divergence to reconcile;
ask-dpa-app's `PKG_SOURCE_VERSION` is identical on both branches, so only the
shipped `files/` config and `PKG_RELEASE` move; 25.12 carries **no** ask-cdx
patches that could fail against the new pin (`mono-ask` has a diagnostic one
from unrelated commits); and the DTS already declares `dpa-fman0-oh@2`.
`cdx_port_of2_policy` lives in the vendor `cdx_pcd.xml` fetched at build, not
in this tree, so it is branch-independent.

`PKG_RELEASE` numbering is kept in lockstep with `mono-ask` — r55 means the
same content on both branches. Reusing r52/r53/r54 on 25.12 for different
content would have made `apk` version comparisons lie.

`PKG_MIRROR_HASH` was copied from the pin verified on `mono-ask` rather than
regenerated here. The tarball derives from the ask-cdx git ref, not from this
tree, so the value is sound in principle — but it is a copy, and that is worth
knowing.

### Verified in the image before trusting the box

The r53 flash failed in a way that looked like a normal flash, so the version
label is not evidence. Checked the staged rootfs, which is what actually went
into the image:

- `build_dir/.../root-layerscape/usr/share/ask-dpa-app/cdx_cfg.xml` carries
  `<port type="OFFLINE" ... portid="9"/>`.
- `build_dir/.../root-layerscape/lib/modules/6.12.94/cdx.ko` contains
  `table %s type %u >= MAX_MATCH_TABLES %u, skipped` — the r55 fix by string,
  not by version number.
- Compiled `cdx_ioctl.h` has `MAX_PORTS_PER_FMAN 16` and
  `MAX_TABLES_PER_FMAN 1024`.
- Image mtime 18:22 is newer than both apks at 18:16, so it picked them up.

### On hardware

Boot at 18:28 IST, six minutes after the image build. The router reports GMT
and the build host runs IST, which briefly made `uptime` look like the box had


### The failsafe was gone, and that makes the result stronger

`/root/cdx-6port-failsafe.sh` and `/root/.cdx-6port-confirmed` do not survive
sysupgrade — `/root` is not on the keep list, unlike `/etc`. So the six-port
boot on 25.12 ran with **no** safety net, and succeeded anyway.

`/etc/rc.local` *was* kept and still hooks the now-absent script. The
`[ -x ... ] &&` guard makes it inert, so this is untidy rather than dangerous,
but it should be removed.

### #33 carried, and this time it is verified on 25.12

The 2026-08-01 note above said the strongswan fix would carry onto 25.12 on
next flash but was not verified there. It is now. `startaction=route`,
`closeaction=hold`, `keyingtries=%forever` and
`/etc/strongswan.d/charon-retry-initiate.conf` (mtime 16:15, pre-flash) all
survived, and `yul_tunnel` established roughly four minutes after boot with no
manual `swanctl --initiate`.

### SELinux came up permissive — not #29, but recorded here

`sestatus` reports `Current mode: permissive` against
`Mode from config file: enforcing`. `/etc/selinux/config` says
`SELINUX=enforcing`, `/proc/cmdline` carries no `enforcing=0`, and nothing in
`/etc/init.d/`, `/etc/rc.local` or `/etc/uci-defaults/` calls `setenforce`. I
did not find the cause and am not guessing at one.

`selinux-policy` is r8 as expected. Five AVC denials this boot, both already
known: three `xtables.subj -> netif.data.file`, and two
`hotplug.call.subj -> mwan3.runtmp.file` — the latter being exactly the #32
survivor that the unbuilt `selinux-policy-r9` addresses.

This contradicts the "SELinux enforcing" claim in `STATE.md`'s production
section, which I have corrected rather than left standing. It wants its own
issue.

### Scope note

All router access was read-only: no `network restart`, no `ifdown`/`ifup`, no
`tcpdump`, no module cycling. Worth noting that the tunnel's local selector
`192.168.12.0/22` contains the management address I was connected from, so
management traffic and the path under test share a subnet on this box — the
opposite of the port isolation `AGENTS.md` asks for, and something to fix
